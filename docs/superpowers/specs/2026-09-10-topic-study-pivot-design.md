# Разбор темы вместо интервью: уровни как данные, скилл генерации, чек-лист — дизайн

Дата: 2026-09-10 · статус: дизайн утверждён владельцем в чате, спека на ревью · три подпроекта A → B → C,
у каждого свой план и PR в `dev`.

## Зачем

Центр тяжести сервиса смещается: не «интервьюер оценивает кандидата», а «я закидываю тему — Kafka,
dbt, что угодно — нейронка раскладывает её на колонки, уровни и вопросы, я разбираю их сам». Проверка
кандидата остаётся вторым режимом на тех же данных. Всё локально; централизованного решения нет.

Что этому мешает сегодня:
- сложность — enum `base | junior | middle | senior`, зашитый в 38 местах бэкенда и фронта плюс
  `styles.css`, `sampler.LEVELS`, `report.ts`; уровни темы Kafka в него не ложатся;
- контент из `content/` попадает в БД только при старте и только в пустой пул (`seed_pool_if_empty`) —
  сгенерированная тема требует рестарта, а перегенерация существующей не применяется вовсе;
- единственный способ что-то отметить на карточке — оценка в сессии с кандидатом.

## Границы

- **Приложение не знает про LLM.** Генерирует скилл Claude Code, пишет файлы в `content/`, сервис их
  импортирует. Ни ключей, ни API-модуля в бэкенде.
- **Пулы `data-engineer` и `data-engineer-x5` не трогаются**: ни файлы, ни уровни. Миграция даёт им
  нынешние четыре уровня как данные, всё остальное — как было.
- **Пул `system-analyst` пересобирается скиллом** (`--fresh`) — это живой гейт подпроекта B.
- Не делаем: spaced repetition, генерацию из приложения, поле «свой ответ», удаление режима интервью.

## Целевая схема

```
/interview-topic Kafka ──▶ content/kafka/pool.yaml (blocks, levels) + content/kafka/<block>/kafka-NN.md
                                │
                                ▼  POST /api/pools/sync  (или старт сервера)
                          БД: pools.levels · nodes (source=seed, upsert по id)
                                │
                                ▼
          доска: колонки × уровни ─ карточка ─ статус known | review | unknown (таблица progress)
                                                          │
                                                          ▼
                                            прогресс по колонке / ряду / направлению
```

## Подпроект A — уровни как данные направления + синхронизация контента

### A1. Модель
- `pool.yaml` получает необязательный список `levels` (порядок = сложность по возрастанию):
  ```yaml
  levels:
    - { id: concepts,  label: Понятия }
    - { id: config,    label: Конфигурация }
    - { id: ops,       label: Эксплуатация }
    - { id: internals, label: Внутренности }
    - { id: design,    label: Проектирование }
  ```
  `id` — slug `[a-z0-9-]`, уникален в пуле; `label` обязателен; 2–8 уровней. Без `levels` пул получает
  `DEFAULT_LEVELS = base «Базовый» · junior «Junior» · middle «Middle» · senior «Senior»` — так остаются
  валидными оба DE-пула и все их файлы.
- `pools.levels` — новый столбец `TEXT NOT NULL` (JSON `[{id,label}]`); `_migrate_pools` в `db.py` добавляет
  его с `DEFAULT_LEVELS` для существующих строк. `PoolCfg.levels: Tuple[LevelCfg, ...]`, `to_dict`/`pool_from_row`/
  `blocks_to_json` получают пару для уровней (`levels_to_json`, `parse_levels`, `normalize_levels`).
- `Node.difficulty: str` (было `Literal`), дефолт убирается — поле обязательно во frontmatter. Импортёр
  проверяет `difficulty ∈ pool.levels` так же, как `block`/`subblock`, с той же формулировкой ошибки.
- `sampler.LEVELS` → порядок из `pool.levels` (передаётся параметром в `filter_nodes`/`matrix_order`/
  `build_interview`); `sessions.plan.difficulties` хранит id уровней — формат не меняется.

### A2. API
- `GET /api/pools`, `GET /api/pools/{id}` отдают `levels`.
- `POST /api/pools` принимает `levels?` (иначе — от пресета, иначе `DEFAULT_LEVELS`); `PUT /api/pools/{id}`
  принимает `levels` по тем же правилам, что `blocks`: уровень вне списка **удаляется вместе с вопросами**
  (confirm с числом в UI), переименование — по `id`.
- `POST /api/pools/sync` (owner) — см. A4. `POST /api/nodes` и `/api/import` валидируют `difficulty` по пулу
  и отвечают 422 с перечнем допустимых.

### A3. Фронт
- `types.ts`: `Difficulty = string`; `PoolConfig.levels: {id,label}[]`; хелперы `levelOrder(pool)`,
  `levelLabel(pool, id)`, `levelColor(pool, id)` рядом с `blockOrder/blockLabel/blockColor`. `DIFFS` и
  `DIFF_COLOR` удаляются; `layout.ts` строит ряды из `levelOrder`.
- Цвет уровня — палитра из 8 цветов по индексу уровня (0 — самый светлый). `styles.css` `.qnode__diff[data-diff=…]`
  заменяется на inline `style` с цветом из `levelColor`; `report.ts` — то же.
- `SetupPage` (чекбоксы уровней), `AddQuestionModal` (select), фильтры доски, шапка рядов — из `levels` пула.
- `BlocksEditor` получает второй, простой список «Уровни» (id генерируется транслитом подписи, ↑ ↓ ✕,
  «+ Уровень»); мастер направления и «Редактировать структуру» показывают его под колонками.
- i18n: новые ключи в `src/i18n/en.ts`; `npm run i18n:check`.

### A4. Синхронизация `content/ → БД`
`sync_pools(db, tenant, content_dir) -> {created, updated, hidden, errors}` в новом модуле `backend/app/sync.py`:
1. `load_pools(content_dir)`; для каждого пула: нет в БД → создать из `pool.yaml`; есть и `deleted_at IS NULL` →
   обновить `label/description/blocks/levels`; есть tombstone → пропустить (удалённое не воскрешаем — как сейчас).
2. Ноды: `load_pool_content(pool)`; upsert по `(tenant, id)` **только** для строк с `source='seed'` или
   отсутствующих; нода с `source='user'` и тем же id — не трогается, попадает в `errors` как конфликт.
3. Нода с `source='seed'`, которой нет в файлах, — `hidden=1` (не удаляется: на неё могут ссылаться оценки).
4. Ошибки импорта файлов — в `errors` тем же форматом, что `/api/graph`.
Вызов: `POST /api/pools/sync` (owner) и **при старте вместо `seed_pool_if_empty`** — поведение перестаёт
зависеть от того, был ли пул пуст. Кнопка «Обновить из файлов» в меню `•••` направления, результат — тост
со сводкой. Сид owner/интервьюера не меняется.

### A5. Гейты A
- `pytest`: новые тесты `test_levels.py` (парсинг `levels`, дефолт, 422 на чужой уровень, удаление уровня с
  вопросами) и `test_sync.py` (создать, обновить, скрыть, конфликт с `user`-нодой, tombstone); старые тесты
  зелёные без правок фикстур (DE-пул на четырёх дефолтных уровнях).
- `npm run build`, `npm run i18n:check`, `npm run smoke` — шаг 1b smoke проверяет четыре подписи оси у
  `data-engineer`; они остаются, тест не правится.
- Ручной: `PUT /api/pools/system-analyst` с пятью уровнями → доска перестраивает ряды; `POST /api/pools/sync`
  после правки одного `.md` → карточка обновилась без рестарта.

## Подпроект B — скилл `interview-topic`

Файл `.claude/skills/interview-topic/SKILL.md` по канону проектных скиллов (`interview-ideas` — образец:
`python-frontmatter`, ground truth через `cat`/`/api/graph`, не Read).

### B1. Вызов и опции
`/interview-topic <тема> [--lang ru|en] [--per-cell N] [--fresh] [--pool <slug>]`. По умолчанию `ru`, `N=2`,
slug — транслит темы.

### B2. Ход
1. **Каркас.** Агент предлагает 3–6 колонок (с под-колонками, где тема этого просит) и 4–6 уровней с
   подписями под тему, показывает таблицей «колонка × уровень» и **ждёт подтверждения** — это единственный
   гейт: каркас дешевле переделать, чем 60 карточек.
2. **Файлы.** `content/<slug>/pool.yaml` (`id`, `label`, `description`, `blocks` с `weight` пропорционально
   числу карточек, `levels`) и карточки `content/<slug>/<block>/<slug>-<block>-NN.md`: frontmatter
   `id, block, subblock?, difficulty, kind: question, title, topic, tags (1–3 из 17 концептов), weight: 1`,
   тело — вопрос и ответ по формату существующих карточек.
3. **Покрытие.** Каждая ячейка колонка × уровень — не меньше `N` карточек; агент печатает матрицу заполнения.
   Вопросы внутри ячейки не дублируют друг друга по смыслу; ответ — 5–15 строк, с примером там, где он уместен.
4. **Публикация.** `POST /api/pools/sync` → `GET /api/graph` → 0 ошибок импорта; иначе агент чинит файлы и
   повторяет. Печатает ссылку `#/board/<slug>`.

Повторный вызов на существующей теме — **дополнение**: сохраняет `pool.yaml`, добавляет карточки в ячейки,
где их меньше `N`, новые id продолжают нумерацию. `--fresh` удаляет каталог и генерирует заново (с confirm).

### B3. Гейт B — пересборка `system-analyst`
`/interview-topic "Системный аналитик" --pool system-analyst --fresh`: свои уровни (не junior/middle/senior),
≥ 2 карточки в ячейке, `sync` без ошибок, `pytest` и `smoke` зелёные (smoke на SA не опирается). Старые 15
карточек SA уходят в git-историю; `data-engineer*` — байт в байт как были (`git diff --stat content/data-engineer*`
пустой — это проверка в плане).

## Подпроект C — чек-лист разбора

### C1. Модель и API
- Таблица `progress (tenant_id, user_id, node_id, status, updated_at)`, PK `(tenant_id, user_id, node_id)`,
  `status ∈ known | review | unknown`. Своё у каждого пользователя; сессии не участвуют.
- `PUT /api/progress/{node_id}` `{status}` (member+), `DELETE` — снять отметку; `GET /api/progress?pool=<id>` →
  `{node_id: status}`; `GET /api/pools` отдаёт `progress: {known, review, unknown, total}` по текущему
  пользователю для карточек на главной.

### C2. Фронт
- Карточка: точка статуса (цвета: known — зелёный, review — янтарный, unknown — красный, нет — пусто).
- Заголовок колонки и ряда: `известно / всего`; тумблер «только неразобранное» в фильтрах toolbar.
- `DetailDrawer`: три кнопки + горячие клавиши `1 / 2 / 3`; после отметки — следующая карточка в порядке
  матрицы (колонка → уровень → id), `Esc` закрывает. Режим сессии этого не показывает — там оценка.
- Главная: у направления — доля `known` полоской; текст «разобрано N из M».

### C3. Гейты C
`test_progress.py` (upsert, изоляция по пользователю, сводка в `/api/pools`), `npm run build`, `i18n:check`,
smoke: новый шаг «отметить карточку → счётчик колонки вырос».

## Решения и отвергнутые альтернативы
- **Уровни свои у темы**, не единая шкала: единая жмёт непохожие темы в одну форму; числовые 1…N без имён —
  на доске непонятны.
- **Скилл, а не API в приложении**: ноль LLM-кода и ключей, подписка вместо оплаты по токенам, результат в git
  и редактируем руками. Кнопка «Новая тема» в UI — возможный четвёртый подпроект, когда захочется.
- **Чек-лист, а не «кандидат = я»**: сессия тянет интервьюера, план и отчёт; для разбора нужен один статус
  на карточке.
- **`sync` upsert-ит только `seed`-ноды**: UI-созданные вопросы (`source='user'`) — вторая истина, файлы её
  не перетирают; конфликт id — ошибка, не тихая перезапись.
- **Скрывать, не удалять** исчезнувшие ноды: на них ссылаются `scores`.
- **Правка ноды из UI переводит её в `source='user'`** (сегодня `PUT /api/nodes/{id}` сохраняет прежний `source`):
  иначе `sync` при следующем старте перетёр бы правку файлом. Цена — такая нода больше не обновляется из файлов.
- **`sync` обновляет конфиг направления без каскадов**: смена колонок/уровней в `pool.yaml` не удаляет вопросы
  (в отличие от `PUT /api/pools`, где это делает пользователь осознанно); скрытые вручную seed-ноды при
  повторном появлении в файлах не разворачиваются — «скрыть» остаётся решением человека.

## Риски
- **A — самый широкий диф** (38 мест + стили + report + sampler). Компенсация: `Difficulty = string` ломает
  типизацию явно там, где остались константы; `tsc` в `npm run build` не даст пропустить.
- Палитра на 8 уровней: при 6+ рядах соседние цвета близки — допустимо, подпись ряда несёт смысл.
- Скилл генерирует 40–80 карточек за вызов — долгий ход; гейт на каркасе и матрица покрытия в выводе
  делают его проверяемым по частям.
- Smoke и `shots.mjs` опираются на DE-пул и его четыре уровня — они не меняются, тесты остаются.
