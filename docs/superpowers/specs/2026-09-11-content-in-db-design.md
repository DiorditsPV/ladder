# Контент в базе, пресеты в репозитории — дизайн

Дата: 2026-09-11. Решение владельца: «не хранить вопросы в репозитории, а заносить их через MCP, но хранить пресеты
вопросов для дата-инженера и системного аналитика. Главный вопрос: как сохранить накопленное и не затереть его».
План из пяти шагов утверждён владельцем целиком.

## Что было опасно
Синхронизация `content/ → БД` на каждом старте сервиса (то есть на каждом деплое):
1. перезаписывала конфиг направлений из `pool.yaml` — правки колонок и уровней через MCP/UI откатывались;
2. прятала seed-карточки, чьи файлы пропали, — удалить вопросы из репозитория значило убрать их с доски;
3. при этом репозиторий был единственной резервной копией контента.

## Решение
1. **Бэкап до любых изменений**: снимок живой базы (`sqlite3` backup API, проверка целостности) на сервере и у
   владельца (`~/dev/backups/ladder/`), плюс JSON-выгрузка всех направлений через API (`deploy/export_json.py`).
2. **Синхронизация только засевает** (`sync.seed_pool`, по умолчанию и на старте): создаёт направление, если его нет,
   и карточки с id, которых нет в тенанте; ничего не перезаписывает и не прячет. Обновление пресета из файлов —
   явное действие владельца: `POST /api/pools/sync?pool=<id>&update=true`, сначала `dry_run=true` (прогон на копии
   БД, отчёт `config_changed`/`hidden`/`conflicts`); в MCP — `sync_from_files`.
3. **В репозитории только пресеты**: `data-engineer`, `system-analyst` и их `-en` (демо). Kafka, Spark и X5 уже в
   живой базе — их каталоги удалены из репозитория (остаются в истории git и в выгрузке); засев их не трогает.
   Тест `test_content_holds_only_presets` фиксирует состав `content/`.
4. **Новое — через MCP/API в живой сайт**: скилл `ladder-topic` заносит направление `write_topic.py --upload`
   (создать или дописать структуру, карточки с явными id, `--overwrite` для правки); `--files` — только пресеты.
5. **Страховка**: `ladder-backup` — снимки в `/var/backups/ladder` (ночной таймер, 14 штук; перед каждым деплоем —
   10 штук); `deploy-ladder.sh` считает видимые карточки по направлениям до и после рестарта и падает, если где-то
   стало меньше; `deploy/backup-pull.sh` забирает снимок и JSON-выгрузку к владельцу.

## Следствия
- Свежая локальная установка содержит только пресеты; полный контент локально — восстановлением снимка.
- Флаги `demo/lang/translation_of` и структура пресета меняются в `pool.yaml` и доезжают до сервера только явным
  обновлением (`update=true`), не деплоем.
- Удалённое направление (tombstone) файлы не воскрешают ни в одном режиме.

## Проверка
pytest: засев не перезаписывает и не прячет, пропускает id, занятые в других направлениях; `update` работает как
раньше; `dry_run` не пишет; `only` ограничивает одним направлением; `write_topic --upload` создаёт, пропускает,
обновляет и дописывает структуру; `ladder-backup` снимает, ротирует, считает и сравнивает. smoke на свежей БД с
пресетами. На сервере: установка страховки, снимок до деплоя и сверка карточек после.
