## Вопрос
Треть событий приходится на один `merchant_id`. Джоб делает inner join с таблицей мерчантов на 50 ГБ, `groupBy(merchant_id)` с `sum` и pandas UDF-медианой, и окно `row_number` по мерчанту. Где хватит AQE и самого Spark, а где нужны salting, двухфазная агрегация или отдельная ветка для горячего ключа?

## Ответ
**Inner join.** Обычно хватает AQE: skew join режет перекошенную партицию событий, копируя к кускам партицию мерчантов. Если сразу за джойном группировка по `merchant_id` и AQE не режет, выбирай: `spark.sql.adaptive.forceOptimizeSkewedJoin=true` — резка ценой лишнего shuffle перед агрегацией, код не меняется; или salting — `salt` 0…N-1 к ключу событий, мерчанты размножены N раз, джойн по `(merchant_id, salt)`: больше кода и данных, зато число кусков задаёшь сам.

**`sum` по мерчанту.** Ничего не нужно: частичная агрегация до shuffle шлёт из таска одну строку на ключ.

**Медиана в pandas UDF.** Частичной агрегации у такого UDF нет: все строки горячего ключа уезжают в один Python-воркер. Двухфазная агрегация — сначала по `(merchant_id, salt)`, потом по `merchant_id` — работает только для разложимых агрегатов: sum, count, min/max, скетчи. Медиана не разложима — замени её встроенным приближением с частичной агрегацией:
```python
res = events.groupBy("merchant_id").agg(
    F.sum("amount"), F.percentile_approx("amount", 0.5))
```

**Окно по мерчанту.** AQE окна не режет, salting ломает нумерацию: треть данных сортирует один таск. Сократи данные до окна или, если логика позволяет, дроби его по `(merchant_id, event_date)`; иначе горячий ключ — отдельной веткой без окна: глобальный `orderBy` раздаёт его по многим таскам, номер даёт `rdd.zipWithIndex()`, затем `unionByName`.

**Не надо** солить заранее: лишний shuffle и размноженный справочник там, где AQE справился бы сам.
