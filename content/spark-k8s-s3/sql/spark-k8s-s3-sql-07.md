## Вопрос
Две Iceberg-таблицы — профили клиентов (2 ТБ) и признаки клиентов (3 ТБ) — несколько раз в день джойнятся по `client_id`, и два shuffle съедают большую часть времени. Стоит ли переразбить обе таблицы по `bucket(N, client_id)` ради storage-partitioned join и когда это не окупится?

## Ответ
Storage-partitioned join убирает shuffle: если обе таблицы разложены одной функцией от ключа, Spark читает бакет k обеих таблиц в одном таске и джойнит без `Exchange`.

**Условия в 3.5.** Одинаковое преобразование в спецификации партиций (`bucket(64, client_id)` с тем же N) и равенство в условии джойна по каждой колонке партиционирования, которую читает запрос: если таблицы разложены ещё и по `days(ts)` и запрос берёт `ts`, он тоже нужен в условии. Лишняя колонка в условии возвращает shuffle, пока не выставлен `spark.sql.requireAllClusterKeysForCoPartition=false`. Плюс два ключа, выключенные по умолчанию:
```python
spark.conf.set("spark.sql.sources.v2.bucketing.enabled", "true")
spark.conf.set("spark.sql.iceberg.planning.preserve-data-grouping", "true")
```
Проверка — под джойном нет `Exchange`, у скана `groupedBy=client_id_bucket`; сортировка внутри таска остаётся.

**Цена.** Таск джойна — бакет целиком: N задаёт параллелизм и размер таска на годы вперёд, а сменить N — значит переписать таблицу. Shuffle не исчезает, а переезжает в запись: каждый писатель раскладывает данные по бакетам. Горячий ключ даёт гигантский бакет, а AQE skew join режет только партиции после shuffle — здесь его нет.

**Не надо,** если одна сторона пролезает в broadcast, если таблицы джойнят по разным ключам (бакетирование помогает одному), если джойн редкий. В Spark 4.x часть ограничений (разное N, джойн по части ключей) снимается отдельными ключами — проверь в своей версии.
