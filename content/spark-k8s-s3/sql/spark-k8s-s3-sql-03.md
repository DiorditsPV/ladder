## Вопрос
Как устроен AQE внутри: в какие моменты выполнения Spark останавливается, чтобы перепланировать запрос, откуда берёт статистику и что может поменять в оставшейся части плана?

## Ответ
AQE исполняет запрос кусками и перепланирует остаток каждый раз, когда очередной кусок посчитан.

**Разрез.** Корень плана — `AdaptiveSparkPlan`. Границы кусков — обмены: каждый `Exchange` (shuffle или broadcast) становится query stage — `ShuffleQueryStage` или `BroadcastQueryStage`. Запускаются те query stage, у которых готовы все дети, — снизу вверх.

**Статистика.** Когда shuffle-стейдж дописал map-выход, драйвер знает точный размер каждой reduce-партиции — не оценку по метаданным, а факт.

**Перепланирование.** С этими цифрами Spark заново прогоняет логический оптимизатор и выбор физических операторов для ещё не запущенной части: пустую сторону джойна схлопывает, маленькую превращает в broadcast. Затем правила, которые меняют только чтение shuffle: склеить мелкие партиции, разрезать перекошенные, читать локально — их след в плане узел `AQEShuffleRead`. Новый план принимается, только если shuffle в нём не больше, чем в текущем.

**Где видно.** `explain()` до запуска печатает `AdaptiveSparkPlan isFinalPlan=false` — это стартовый план. Итоговый, с `isFinalPlan=true` и секциями Final Plan / Initial Plan, — после выполнения во вкладке SQL в Spark UI; `explain()` покажет его, только если исполнялся сам этот DataFrame (`collect()`): `count()`, `show()` и запись строят новый запрос.

**Пределы.** Первый стейдж со сканом планируется по статическим оценкам; запросу без обменов адаптировать нечего; уже запущенный стейдж не меняется — решения принимаются только на границах.
