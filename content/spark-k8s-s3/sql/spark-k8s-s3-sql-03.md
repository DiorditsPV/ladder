## Вопрос
Как устроен AQE: в какие моменты Spark перепланирует запрос во время выполнения, откуда берёт статистику и что может поменять?

## Ответ
AQE исполняет запрос кусками и перепланирует остаток каждый раз, когда очередной кусок посчитан.

**Разрез.** Корень плана — `AdaptiveSparkPlan`. Границы кусков — обмены: каждый `Exchange` (shuffle или broadcast) становится query stage. Запускаются те query stage, у которых готовы все дочерние, — снизу вверх.

**Статистика.** Когда shuffle-стейдж дописал свой выход, драйвер знает точный размер каждой партиции — не оценку по метаданным, а факт.

**Перепланирование.** С этими цифрами Spark заново оптимизирует ещё не запущенную часть плана: пустую сторону джойна схлопывает, маленькую превращает в broadcast. Затем применяет правила, которые меняют только чтение shuffle: склеить мелкие партиции, разрезать перекошенные, читать локально — их след в плане узел `AQEShuffleRead`. Новый план принимается, только если shuffle в нём не больше, чем в текущем.

**Где видно.** `explain()` до запуска печатает `AdaptiveSparkPlan isFinalPlan=false` — это стартовый план. Итоговый, с `isFinalPlan=true`, смотрят после выполнения во вкладке SQL в Spark UI; `explain()` покажет его, только если исполнялся сам этот DataFrame через `collect()` — `count()`, `show()` и запись строят новый запрос.

**Пределы.** Первый стейдж со сканом планируется по статическим оценкам; запросу без обменов адаптировать нечего; уже запущенный стейдж не меняется — решения принимаются только на границах.
