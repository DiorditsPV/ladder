## Вопрос
Чем OOMKilled пода экзекьютора отличается от java.lang.OutOfMemoryError: Java heap space в логе экзекьютора?

## Ответ
Это две разные границы памяти, и срабатывают они у разных сторожей.

**Java OutOfMemoryError** — закончился heap внутри JVM. Исключение бросает сама JVM, в логе экзекьютора есть стек. Spark считает ошибку фатальной: процесс экзекьютора завершается (в логе драйвера — `exit code 52`), а таск перезапускается на другом экзекьюторе. Причина обычно в данных: слишком большая партиция, перекос ключа, `collect_list` по огромной группе.

**OOMKilled** — весь контейнер превысил лимит памяти пода, и ядро Linux убивает его сигналом SIGKILL. Стека нет, лог просто обрывается; в логе драйвера — `exit code 137`, а в статусе контейнера — `OOMKilled`. Heap в этот момент может быть наполовину пуст: лимит съела память вне heap — Python-воркеры, нативные буферы, off-heap.

Пример на PySpark: UDF загружает модель на 1 ГБ. На экзекьюторе с 8 ядрами работают 8 Python-воркеров, у каждого своя копия модели, — это 8 ГБ вне JVM, и под убивают, хотя heap в порядке.

Поэтому и лечат по-разному: Java OOM — дроблением данных (больше партиций, борьба с перекосом) или большим heap; OOMKilled — памятью вне heap (overhead) или меньшим числом ядер на экзекьютор, то есть меньшим числом одновременных Python-воркеров.
