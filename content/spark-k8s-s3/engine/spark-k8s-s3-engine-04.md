## Вопрос
Почему Python UDF замедляет джоб и чем его заменить: встроенными функциями или pandas UDF?

## Ответ
Python UDF медленный не из-за самого Python, а из-за перегонки данных: функция исполняется в отдельном Python-процессе рядом с JVM экзекьютора, и каждую строку нужно сериализовать туда и обратно. Кроме того, для оптимизатора UDF — чёрный ящик: фильтр с UDF не дойдёт до чтения данных.

**Первый выбор — встроенные функции** (`regexp_replace`, `split`, `when`, `date_trunc`, джойн со справочником вместо словаря в коде). Они работают внутри JVM, без Python-процесса, и видны оптимизатору.

**Если без Python не обойтись — pandas UDF.** Данные идут в воркер колоночными батчами через Arrow, функция получает `pd.Series` и обрабатывает сразу пачку строк:
```python
@F.pandas_udf("string")
def norm(s: pd.Series) -> pd.Series:
    return s.str.strip().str.lower()
```
Векторизуемая логика (методы `.str`, numpy) ускоряется кратно. Если внутри всё равно построчная библиотека, выигрыш будет только на передаче данных.

**Обычный Python UDF** (`@F.udf`) оставляют для небольших объёмов и логики, которую не выразить иначе. С 3.5 у него есть `useArrow=True`: передача через Arrow при построчном вызове.

Память Python-воркеров живёт вне heap экзекьютора — её нужно закладывать в ресурсы пода.
