## Вопрос
PySpark-джоб отбрасывает битые телефоны Python UDF в `filter` и внутри неё считает их аккумулятором, потом делает `count()` для лога и пишет результат в Iceberg. После записи аккумулятор показывает 1,6 млн, хотя проверка источника SQL-запросом даёт около 800 тыс. Почему так и как считать правильно?

## Ответ
**Причина — ленивость.** UDF с `bad.add(1)` — часть трансформации: она выполняется не при объявлении, а каждый раз, когда действие вычисляет DataFrame. `count()` и запись — два действия, оба заново читают S3 и прогоняют фильтр с UDF по всем строкам, отсюда ровно удвоение. Будь UDF лишь в `withColumn`, `count()` её бы не вызвал: ненужную для подсчёта колонку оптимизатор выбрасывает.

Сверху могут добавить и другие пересчёты: повтор упавшего таска, speculative-копия, перезапуск стейджа после потери экзекьютора, потеря кеша вместе с экзекьютором. Однократный учёт Spark гарантирует только для обновлений внутри действий (`foreach`, `foreachPartition`); в трансформациях обновление таска может примениться несколько раз. К тому же оптимизатор вправе вызвать UDF больше раз, чем она встречается в запросе.

**Как подтвердить:** в Spark UI у джобов `count()` и записи одинаковый Input из S3 — источник читался дважды.

**Как считать:** метрику качества — из самих данных, а не из побочного эффекта:
```python
ok = F.coalesce(F.col("phone").rlike("^7[0-9]{10}$"), F.lit(False))
checked = src.withColumn("phone_ok", ok).cache()
bad_cnt = checked.filter(~F.col("phone_ok")).count()
checked.filter("phone_ok").drop("phone_ok").writeTo("lake.db.clients").append()
```
Даже если кеш потеряется и партиции пересчитаются, число останется верным: оно выводится из строк. Битые строки можно ещё и писать в карантинную таблицу. Аккумуляторы оставь для приблизительной диагностики.
