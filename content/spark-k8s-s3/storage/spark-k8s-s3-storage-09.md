## Вопрос
Как выбрать колонки для партиционирования таблицы на S3 и почему партиций не должно быть слишком много?

## Ответ
Партиционируют по колонке, по которой фильтрует большинство запросов, — обычно по дате — и так, чтобы партиции оставались крупными: ориентир — от сотен мегабайт на партицию, а самих партиций тысячи, а не миллионы.

**Хорошая колонка для партиции:**
- по ней фильтрует большинство запросов — тогда Spark не читает лишние каталоги;
- у неё немного значений — дата, регион из десятка значений;
- она не меняется у записи: дата создания — да, статус заказа — нет, иначе обновление пришлось бы переносить строку между каталогами.

**Плохая колонка** — уникальные или почти уникальные ключи (`order_id`, `user_id`): каталог на каждое значение и миллионы крошечных файлов. Поиск по такому ключу — задача раскладки строк внутри файлов (сортировка, статистики), а не каталогов.

**Почему партиций не должно быть много.** Каждая партиция — каталог и хотя бы один файл. Кардинальности перемножаются: дата × регион × канал быстро дают десятки тысяч партиций в год. Растут число мелких файлов, время листинга на S3 и нагрузка на метастор, а запрос за месяц открывает тысячи крошечных файлов.

**Ловушки.** Значение партиции пишет сам джоб, и Hive-таблица не проверит, что `dt` совпадает с датой в данных: запрос с фильтром по другой колонке с датой прочитает всю таблицу. Сменить схему партиций можно только полной перезаписью. Таблицу в единицы гигабайт лучше не партиционировать вовсе, а если схема будет меняться — взять Iceberg со скрытым партиционированием.
