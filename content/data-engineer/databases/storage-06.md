## Вопрос
Что важно учитывать, используя S3 как хранилище data lake: партиционирование по префиксам, стоимость LIST, проблема мелких файлов?

## Ответ
- **Партиционирование = структура префиксов** ключа (`s3://bucket/table/dt=YYYY-MM-DD/...`). Движки (Spark/Trino) делают partition pruning по пути → читают только нужные префиксы. Плохая схема (слишком гранулярные партиции, например по минутам) даёт взрыв числа объектов.
- **Стоимость и медленность LIST:** чтобы узнать файлы партиции, движок делает LIST по префиксу — платный (за запросы) и медленный при сотнях тысяч объектов. Метастор (Hive Metastore / Glue) или табличные форматы (Iceberg/Delta/Hudi) хранят список файлов в манифестах → избегают дорогого листинга.
- **Мелкие файлы:** как и в HDFS, множество мелких объектов → много LIST/GET, оверхед открытия, мелкие неэффективные таски. Лечат компакцией под целевой размер (128–512 МБ), `coalesce`/`repartition` на записи.

Плюс: atomic-rename нет → нужны S3-aware committers (отдельная тема). Распределение по префиксам влияет и на throughput запросов.
