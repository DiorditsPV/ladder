## Вопрос
Событие из общего топика читают пять команд, нужно переименовать поле и сменить тип другого. Как провести миграцию, не останавливая никого?

## Ответ
Сначала — какое из двух изменений действительно ломающее. Смена типа запрещена не всякая: Avro разрешает **промоцию** — `int → long → float → double` и `string ↔ bytes`, такая версия проходит проверку и читателей не задевает. Рвут контракт обратные и несвязанные переходы: `long → int`, `int → string`, примитив вместо структуры. Переименование ломающее всегда — Avro видит его как удаление одного поля и добавление другого.

**Расширение вместо замены.** Новое поле добавляется рядом со старым, с дефолтом, и какое-то время пишутся оба. Это совместимое изменение: проходит `FULL` и не трогает существующих читателей.

Порядок шагов. Зарегистрировать новую версию схемы и выкатить продюсера, заполняющего оба поля. Выждать ретеншен топика — до этого в нём есть записи только со старым полем. Перевести пять команд на новое поле, каждую в своём темпе, с подтверждением. Удалить старое поле — теперь это совместимое удаление поля с дефолтом.

Для последнего шага нужен явный владелец топика и список читателей (`kafka-consumer-groups.sh --list`), иначе старое поле живёт вечно.

Компромисс, который стоит обсудить: если растягивать миграцию дорого, дешевле завести **новый топик** новой версии, писать в оба, перевести читателей и погасить старый — честнее, чем схема с дублирующими полями, но вдвое дороже по объёму.

Чего делать нельзя: ослаблять режим совместимости до `NONE`, чтобы протолкнуть схему, — ровно после этого в проде падают чужие сервисы.
