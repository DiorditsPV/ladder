## Вопрос
Sink-коннектор перестал выгружать данные и висит в статусе FAILED. Как посмотреть причину, перезапустить и что будет с позицией?

## Ответ
Всё делается через REST API кластера Connect.

Статус и причина: `GET /connectors/orders-sink/status` возвращает состояние самого коннектора и каждой задачи отдельно с трассировкой исключения в поле `trace`. Важная деталь: коннектор может числиться `RUNNING`, а задачи внутри быть `FAILED` — общий статус смотреть недостаточно, данные при этом не идут.

Перезапуск: `POST /connectors/orders-sink/restart?includeTasks=true&onlyFailed=true` поднимает коннектор вместе с упавшими задачами. Отдельная задача перезапускается через `POST /connectors/orders-sink/tasks/0/restart`.

С позицией ничего не происходит: sink-коннектор — обычная consumer group с именем вида `connect-orders-sink`, и её offset'ы лежат в `__consumer_offsets`. После перезапуска обработка продолжится с последнего коммита, поэтому часть записей будет обработана повторно — sink должен быть идемпотентным. Source-коннектор хранит позицию в источнике в топике `connect-offsets` и продолжает с неё.

Перезапуск помогает, только если причина временная — недоступность целевой системы, таймаут. Если задача падает на конкретной записи (несовместимая схема, битый JSON), она будет падать снова. Тогда: чинить целевую систему либо включить `errors.tolerance=all` вместе с `errors.deadletterqueue.topic.name`, чтобы такие записи уходили в DLQ, а не терялись молча. Какая именно запись сбойная — видно в логах Connect по топику, партиции и offset.
