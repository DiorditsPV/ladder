## Вопрос
Что задают replication.factor и min.insync.replicas и как выбрать их пару, если брокеров три?

## Ответ
**`replication.factor`** — сколько копий партиции держит кластер. Задаётся при создании топика и определяет, сколько брокеров может выйти из строя, не потеряв данные физически.

**`min.insync.replicas`** — сколько реплик обязаны подтвердить запись, чтобы она считалась принятой. Настройка работает только вместе с `acks=all` на продюсере: при `acks=1` лидер отвечает сам и `min.insync.replicas` ни на что не влияет — это самая частая ошибка в конфигурации.

Для трёх брокеров рабочая пара — `replication.factor=3`, `min.insync.replicas=2`. Что она даёт: запись подтверждена, когда её приняли минимум два брокера, значит потеря одного брокера не теряет подтверждённых данных, и кластер продолжает принимать запись при одном упавшем узле.

Почему не `min.insync.replicas=3`: тогда падение любого брокера останавливает запись — продюсер получает `NotEnoughReplicasException`. Почему не 1: подтверждённая только лидером запись исчезнет вместе с ним. Правило: `replication.factor - min.insync.replicas` — это число брокеров, которое можно потерять без остановки записи, а `min.insync.replicas - 1` — без потери данных.

`replication.factor=1` допустим только для данных, которые не жалко: рестарт брокера делает партицию недоступной, отказ диска — уничтожает.

Проверить фактическое состояние: `kafka-topics.sh --describe --topic orders` — колонка Isr показывает реплики, реально успевающие за лидером.
