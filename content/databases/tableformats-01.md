## Вопрос
Зачем нужны табличные форматы (Apache Iceberg / Hudi / Delta Lake) поверх parquet? Какие проблемы «голого» parquet на S3/HDFS они решают?

## Ответ
«Голый» parquet — это просто набор файлов в директории/префиксе; СУБД-семантики над ними нет. Отсюда проблемы:
- нет атомарности — читатель может увидеть полузаписанный набор файлов;
- нет транзакций и безопасной конкурентной записи;
- дорогой и неатомарный LIST на S3, чтобы узнать состав таблицы;
- болезненная эволюция схемы и партиционирования (часто = переписать данные);
- нет time travel; компакция мелких файлов и построчные DELETE/UPDATE — вручную.

Табличные форматы добавляют **слой метаданных** (лог транзакций / манифесты) поверх тех же parquet-файлов и дают:
- **ACID-транзакции** и snapshot-изоляцию (атомарный commit набора файлов);
- **эволюцию схемы и партиционирования** без переписывания данных;
- **time travel** (чтение по версии/времени) и rollback;
- безопасную конкурентную запись (optimistic concurrency);
- быстрый план без дорогого LIST — список файлов берётся из метаданных + статистика для file pruning;
- `MERGE`/`DELETE`/`UPDATE` и компакцию мелких файлов.

Реализации: Delta Lake (лог `_delta_log`), Iceberg (снапшоты + манифесты), Hudi (copy-on-write / merge-on-read). По сути они превращают data lake в **lakehouse**.
