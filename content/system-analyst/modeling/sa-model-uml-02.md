## Вопрос
Для заявки/заказа со сложным жизненным циклом (создание → согласование → выполнение → закрытие, с возвратами и отменами) — как спроектировать модель состояний и на что обратить внимание?

## Ответ
Начинают с **диаграммы состояний (state machine diagram)**: состояния — узлы (черновик, на согласовании, в работе, приостановлен, выполнен, отменён), переходы — рёбра с условием и, часто, действием («согласовано → в работе», «истёк таймаут ожидания → эскалация»).

Ключевая часть проектирования — **инварианты переходов**: явно перечислить, какие переходы вообще допустимы (нельзя из «черновика» сразу в «выполнен»), и какие предусловия нужны для каждого (нельзя закрыть заявку с непогашенным блокером) — это защищает от невозможных состояний, а не только описывает happy path. Для каждого перехода фиксируется **владелец** — кто или что его инициирует: пользователь через UI, система по таймауту, внешнее событие от интеграции — и это влияет на модель доступа и аудит («кто перевёл заявку в отменённые»).

В базе данных состояние обычно хранится не только как текущее значение (`status` enum), но и **историей переходов** в отдельной таблице (entity_id, from_state, to_state, actor, timestamp, reason) — это нужно и для аудита, и для отчётов по времени в каждом состоянии, и для отладки «почему заявка застряла». Переходы стоит защищать **на уровне БД или сервиса**, а не только на UI: разрешённая матрица переходов проверяется в бэкенде (или через триггер/constraint), иначе гонка запросов или прямой вызов API в обход UI создаст недопустимое состояние.

В API это отражается явными эндпоинтами действий («POST /orders/{id}/cancel»), а не универсальным «PATCH status=любое значение» — так контракт сам ограничивает допустимые переходы и не даёт клиенту выставить произвольный статус. Отдельно стоит продумать **конкурентные переходы** — что если два актора одновременно пытаются перевести сущность в разные состояния: нужна версия/optimistic lock, чтобы второй переход либо провалился с понятной ошибкой, либо переиграл логику с актуальным состоянием.
