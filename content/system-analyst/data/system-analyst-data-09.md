## Вопрос
Что аналитику нужно знать про транзакции и уровни изоляции, чтобы правильно описывать конкурентные сценарии?

## Ответ
Транзакция — группа операций, которая применяется целиком или не применяется вовсе. Для аналитика это способ сформулировать требование «списание резерва и создание заказа происходят вместе, промежуточного состояния не существует».

Проблемы конкурентного доступа, которые описываются в требованиях:
- **Потерянное обновление** — два оператора читают остаток 5, каждый вычитает 3 и пишет 2; списано 6, в базе 2.
- **Неповторяющееся чтение** — внутри одной операции одно и то же значение прочитано дважды и оказалось разным.
- **Фантомы** — повторный запрос по условию возвращает новые строки, появившиеся между чтениями.

Уровни изоляции — это выбор, какие из этих эффектов запрещены. READ COMMITTED (типичный по умолчанию) убирает грязное чтение, но допускает неповторяющееся; REPEATABLE READ и SERIALIZABLE закрывают больше, платя блокировками, откатами транзакций и падением пропускной способности.

Практический вывод для проектирования: вместо повышения уровня изоляции для всей системы описывают защиту конкретного места — уникальный индекс на бизнес-ключ, атомарное условное обновление (`UPDATE … WHERE qty >= :n`), явную блокировку строки. Это дешевле и предсказуемее.

Что от аналитика требуется в спецификации: назвать сценарий гонки словами, указать ожидаемый результат («второму оператору показывается ошибка "товар уже зарезервирован"») и определить, что видит пользователь при откате. Без этого разработчик выберет поведение сам, и оно всплывёт в поддержке.

Отдельно стоит помнить границу: транзакция работает внутри одной базы. Согласованность между сервисами транзакцией не обеспечивается и требует другого механизма.
