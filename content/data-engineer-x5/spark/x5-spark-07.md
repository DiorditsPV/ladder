## Вопрос
Какие бывают физические алгоритмы джойна в реляционной СУБД и какие стратегии джойна есть в Spark? Когда выбирается каждая?

## Ответ
В реляционной СУБД три классических алгоритма. Nested loop: для каждой строки внешней таблицы проход по внутренней; в лоб это O(N·M), но если по внутренней стороне есть индекс по ключу джойна, каждый проход превращается в поиск по индексу, и для маленькой внешней стороны это самый быстрый вариант. Hash join: по меньшей таблице строится хэш-таблица в памяти, по большей делается один проход с поиском в ней; работает только для равенства, выигрывает на больших объёмах, требует памяти под хэш-таблицу — если её не хватает, разбивается на батчи с записью на диск. Merge join: обе стороны отсортированы по ключу и сливаются одним проходом; выгоден, когда данные уже упорядочены (индекс, предыдущая сортировка), иначе к нему добавляется стоимость двух сортировок.

В Spark набор похож, но с поправкой на распределённость. BroadcastHashJoin: маленькая сторона рассылается на все экзекьюторы, шафла нет; выбирается при размере ниже порога бродкаста или по хинту. SortMergeJoin — стратегия по умолчанию для двух больших таблиц: обе шафлятся по ключу, партиции сортируются и сливаются; устойчив к нехватке памяти, потому что сортировка умеет сбрасываться на диск. ShuffledHashJoin: тоже шафл по ключу, но вместо сортировки по меньшей стороне каждой партиции строится хэш-таблица; быстрее merge, если сторона умещается в память, включается хинтом или при подходящих оценках. BroadcastNestedLoopJoin и CartesianProduct — фолбэк для условий без равенства (`<`, `between`, `like`) и для кросс-джойнов; самый дорогой вариант, и его появление в плане обычно означает ошибку в условии.

Общая логика одна и та же в обоих мирах: hash — для равенства и больших объёмов при достаточной памяти, merge — когда порядок уже есть или память ограничена, nested loop — когда одна сторона крошечная или условие не сводится к равенству. Разница в том, что в СУБД выбор делает оптимизатор по статистике и индексам, а в Spark к этому добавляется стоимость шафла, из-за которой broadcast становится главным приёмом.
