## Вопрос
Что даёт табличный формат вроде Apache Iceberg по сравнению с каталогом Parquet-файлов в S3? Как он устроен и какие операции становятся возможны?

## Ответ
Каталог Parquet-файлов — это набор файлов без общего понятия «таблица». Список файлов узнаётся обходом хранилища (в S3 — медленный листинг), партиции — из имён каталогов, схема — из первого попавшегося файла. Отсюда проблемы: писатель и читатель могут увидеть полузаписанное состояние, обновление строки означает переписать файл и надеяться, что его никто не читал в этот момент, смена схемы или схемы партиционирования — миграция всех данных.

Iceberg добавляет над файлами слой метаданных. Таблица — это указатель на текущий файл метаданных; тот хранит список снапшотов; снапшот — manifest list; манифесты перечисляют файлы данных с их статистикой (min/max по столбцам, число строк, партиция). Каждая запись создаёт новый снапшот и атомарно переключает указатель в каталоге (Hive Metastore, REST, Nessie и другие). Читатель всегда видит целостный снапшот; параллельные писатели коммитят оптимистично — кто не успел переключить указатель, перечитывает метаданные и повторяет. Так получаются ACID-коммиты поверх объектного хранилища.

Из этой конструкции следуют возможности. Планирование запроса без листинга: файлы и их статистика берутся из манифестов, отсечение партиций и файлов по предикатам делается по метаданным. Скрытое партиционирование: партиция — функция от столбца (`days(ts)`, `bucket(16, id)`), запрос фильтрует по исходному столбцу, а Iceberg сам применяет преобразование; схему партиционирования можно менять без переписывания старых данных. Эволюция схемы — добавить, переименовать, удалить столбец — только в метаданных, по идентификаторам столбцов, без переписывания файлов. Time travel и откат: запрос по снапшоту или по времени, возврат к предыдущему состоянию. Построчные `UPDATE`, `DELETE`, `MERGE INTO` — через copy-on-write (переписать затронутые файлы) или merge-on-read (формат v2: delete-файлы, применяемые при чтении).

Цена — обслуживание: снапшоты нужно истекать, мелкие файлы — компактировать, сиротские файлы — чистить. Без этого метаданные распухают, а чтение с накопленными delete-файлами замедляется. Каталог становится единой точкой согласованности: все движки (Spark, Trino, Flink) должны ходить через него, а не читать файлы напрямую.
