## Вопрос
На таблице `t` есть индекс `(a, b)`. Применится ли он в каждом из запросов, и будет ли index-only scan? Как переделать индекс, чтобы стал?
```sql
SELECT a, b, c FROM t WHERE a = 5;    -- запрос 1
SELECT a, b, c FROM t WHERE b = 5;    -- запрос 2
```

## Ответ
Первый запрос индекс использует: `a` — ведущий столбец, а составной B-tree упорядочен сначала по `a`, затем по `b`, поэтому по условию на `a` можно спуститься к нужным листьям. Это правило leftmost-prefix: составной индекс работает для условий на любой левый префикс его столбцов — `(a)`, `(a, b)`, но не на `(b)` в отрыве от `a`.

Но index-only scan здесь не получится. В индексе есть `a` и `b`, а запрос просит ещё и `c`; за ним придётся сходить в таблицу по указателю из листа — heap fetch на каждую найденную строку. Это обычный Index Scan. Чтобы СУБД обошлась одним индексом, он должен быть покрывающим: содержать все столбцы, которые запрос читает. Варианты — включить `c` в ключ, `(a, b, c)`, либо в Postgres добавить неключевой столбец: `(a, b) INCLUDE (c)`. Второй вариант лучше: `c` не участвует в упорядочении, не раздувает внутренние узлы и не влияет на порядок листьев. Отдельная тонкость Postgres — даже покрывающий индекс не спасает от похода в heap, если страница не помечена как полностью видимая в visibility map; после массовых изменений помогает `VACUUM`.

Второй запрос индекс `(a, b)` не использует. Ключи отсортированы по `a`, и внутри дерева значения `b = 5` разбросаны по всем поддеревьям — без условия на `a` нет точки, куда спуститься. Планировщик выберет последовательный скан (в редких случаях — полный обход индекса, если он сильно меньше таблицы, но это перебор, а не поиск). Для второго запроса нужен отдельный индекс с ведущим `b` — например `(b)` или `(b, a)`.

Отсюда практическое правило проектирования составных индексов: ведущим ставится столбец, по которому фильтруют всегда, а порядок столбцов важнее их набора.
