## Задача
По таблице `bookings` (схема в стартовом коде) выведи `building, floor, n_clients` — корпус и этаж, где за декабрь 2024 остановилось наибольшее число человек. После написания прогони запрос мысленно на двух-трёх строках данных.

## Эталон
Опорное решение — один CTE с агрегатом и снятие вершины оконной функцией:
```sql
with counted as (
    select building, floor, count(distinct client_id) as n_clients
    from bookings
    where date >= date '2024-12-01' and date < date '2025-01-01'
    group by building, floor
)
select building, floor, n_clients
from counted
qualify row_number() over (order by n_clients desc) = 1;
```
Если диалект не знает `QUALIFY`, тот же CTE оборачивается в подзапрос с `where rn = 1`; годится и `order by n_clients desc limit 1`, если ничьи не важны.

Что здесь проверяется. Первое — дедупликация: один клиент мог забронировать десять ночей на этаже, и это один человек, а не десять; отсюда `count(distinct client_id)` вместо `count(*)`. Второе — `client_id` nullable. `count(distinct ...)` молча отбрасывает NULL, и в этой задаче это как раз нужно, но решение должно быть осознанным: строки без клиента не считаем, а если их заметная доля — это вопрос к бизнесу, а не к запросу. Отдельные CTE для дедупа и фильтрации NULL не нужны — агрегат делает всё сам. Третье — фильтр по дате: `like '2024-12%'` работает только на строке; по столбцу типа `date` нужен полуоткрытый диапазон (или `date_trunc`), который к тому же позволяет использовать индекс. Четвёртое — ничьи: `row_number` вернёт одну строку, `rank` — всех лидеров с одинаковым максимумом; правильный ход — спросить, нужен один или все.

Классическая ошибка — `select building, floor, max(n_clients)` без `group by`: агрегат вместе с неагрегированными столбцами либо отвергается СУБД, либо (в диалектах с послаблениями) возвращает произвольную пару `building, floor`, не связанную с максимумом. Вторая типичная ошибка — сортировка без `desc`: запрос выглядит правильно и возвращает минимум. Прогон на трёх строках ловит и то, и другое.
