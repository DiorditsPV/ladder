# Проверка результата

Работай из корня фактического checkout, сверяясь с текущим `AGENTS.md`.
Для контента прочитай [общий стандарт качества](../ladder-topic/references/content-quality.md).
Редакционная и техническая проверки дают разные виды доказательств; сообщай их раздельно.

## Редакционная проверка

Для новой/пересобранной доски проверь карту всей темы, для точечных правок — изменённые карточки
и затронутые предпосылки. Проверь существенность, отсутствие дублей, понятный порядок,
уровни, явные термины, прямой достаточный ответ и полезность примеров.

Открой источники и сопоставь ключевые утверждения с конкретными разделами, версиями и условиями.
Проверь отдельно авторские выводы. Наличие ссылки и HTTP 200 не подтверждают содержание ответа.
Если не удалось проверить тезис, укажи его как непроверенный; успешный импорт не отменяет эту находку.

## Фактическое место записи

Установи точный базовый URL, ID пула и способ изменения — seed-файлы или MCP/API.
После записи перечитай именно это направление из того же сервиса и сверь ID, количество,
вопросы, ответы, уровни и структуру с подготовленным результатом.
Локальная запись не означает публикацию; sync видит только content файловой системы сервера,
а старт сервера и sync без параметров только засевают недостающее — пресет обновляется явно
(`POST /api/pools/sync?pool=<id>&update=true`, сначала `dry_run=true`).
Закрытые направления проверяй авторизованным чтением, а не анонимным демо-API.

Открой доску и изменённые карточки: проверь порядок чтения, выделение терминов, ссылки, таблицы,
fenced code и ожидаемые результаты примеров. Представительные карточки должны охватить каждый
использованный вид форматирования; тексты всех изменённых карточек сверь после чтения обратно.
Особенно проверь, что импортер не обрезал ответ на строке `# ...` внутри кода.
Если UI-проверка недоступна, явно отдели проверенное содержимое API от непроверенного отображения.

## Технические проверки по объёму изменений

| Изменение | Проверки |
| --- | --- |
| Только инструкции скиллов | Валидность SKILL.md, существование ссылок, отсутствие противоречий, сценарии применения |
| Помощник скилла | Целевые тесты изменённого поведения и сохранности файлов/данных |
| Seed-контент | Импорт без ошибок, pytest, smoke на изолированной БД; фронт не требует пересборки |
| Backend / модель / импорт | Импорт, pytest, необходимые проверки затронутого API |
| Frontend | `npm run build`, `npm run i18n:check`, smoke на изолированной БД |
| Контент через MCP/API без правки кода | Ответ операции, чтение обратно, импортные ошибки графа, редакционное и визуальное ревью |

Для доступного API можно запустить помощник (в `API_URL` входит `/api`):

```bash
API_URL=http://127.0.0.1:8000/api POOL=data-engineer python3 .claude/skills/interview-verify/check_import.py
```

Адрес/пул — пример, сначала подставь нужные. Скрипт проверяет ошибки импорта и отсутствие тегов,
но не доказательность ответов. При недоступном или закрытом API используй авторизованное чтение;
локальные файлы можно проверить через `app.pools.load_pools` и `app.importer.load_pool_content`
в `backend/.venv`. Ошибки должны завершать проверку с ненулевым кодом.

Backend-тесты: `backend/.venv/bin/python -m pytest backend/tests -q`.
Если проверка поднимает приложение, передай `INTERVIEW_DB_PATH` с новым временным путём.
Для smoke сначала прочитай актуальные `frontend/smoke.mjs` и `AGENTS.md`: smoke создаёт аккаунты
и изменяет данные, поэтому запускай его только против отдельного тестового сервера со свежей БД.
Освобождай нужный порт без остановки чужих процессов; управляй только процессом, который запустил сам.
Не используй массовый `pkill` и не удаляй пользовательскую БД ради проверки.

Фронтовые команды запускай из `frontend/`. При изменении селекторов/заголовков обнови затронутые smoke-проверки.
Перезапуск нужен только для фактически изменённого приложения; правка текста скилла его не требует.
В финале укажи выполненные проверки и их результат, точный адрес доски при публикации и оставшиеся ограничения.
