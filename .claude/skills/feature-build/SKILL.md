# Скилл: реализация фичи (build по спеке, в ветке фичи)

Реализует то, что спроектировал **feature-design**. Код пишем, но строго по спеке и в ветке фичи.

## 0. Взять спеку
- Найди спеку: `ls .claude/features/` → возьми названную пользователем, иначе последнюю со `status: designed|building`. Прочти через `cat` (НЕ Read — кэш). Если спеки нет — предложи сначала запустить **feature-design**, не выдумывай фичу сам.

## 1. Ветка фичи (ОБЯЗАТЕЛЬНО — не работать в main)
- Проверь репозиторий: `git rev-parse --is-inside-work-tree`. Если не git — предупреди пользователя и спроси: `git init` или продолжать без ветки (по умолчанию НЕ продолжать молча).
- Проверь чистоту дерева: `git status --porcelain`. Если есть чужие незакоммиченные правки — спроси, как быть (не затирай).
- Создай/переключись на ветку от актуальной default-ветки:
  ```bash
  git switch -c feature/<slug> 2>/dev/null || git switch feature/<slug>
  ```
  Никогда не коммить фичу прямо в `main`/`master`.
- В спеке выставь `status: building`.

## 2. Реализовать по плану — ПЕРЕИСПОЛЬЗУЯ скиллы
Иди по чеклисту «План реализации» из спеки, отмечая шаги `[x]`. Не дублируй логику существующих скиллов —
**вызывай их через Skill-инструмент**:
- контент/вопросы (создать, развернуть, реализовать идеи в ноды) → **interview-ideas**;
- правка сложности / тегов / подачи существующих вопросов → **interview-refactor**;
- оценка покрытия и пробелов (если фича про наполнение) → **interview-balance**;
- любая проверка по ходу и в конце → **interview-verify**.
Также используй их вспомогательные скрипты при нужде: `interview-refactor/inventory.py`,
`interview-balance/coverage.py`, `interview-verify/check_import.py`, `interview-ideas/regen_ledger.py`.

Конвенции проекта (см. карту в feature-design): ground truth через `cat`/`/api/graph`, НЕ Read; контент —
через `python-frontmatter` (нормализованный формат); рёбер не добавлять; теги только из 17; difficulty
base→senior; под-колонки через `subblock`; модель `Node` имеет `extra="forbid"` (новое поле = правка
`models.py` + `types.ts`); новый тип ноды на канве = регистрация в `nodeTypes` (App.tsx).

## 3. Гейт качества (verify + code-review)
1. Прогони **interview-verify** + проверки из раздела «Тесты/приёмка» спеки:
   - контент-only → import (0 ошибок) + pytest + smoke;
   - правка `frontend/src` → ещё `npm run build` + при переименованиях обнови `frontend/smoke.mjs`;
   - правка `backend/app` → import + pytest. Доводи до «ALL SMOKE CHECKS PASSED ✓» (по возможности — скриншот).
2. Прогони **code-review** по диффу ветки; краткое резюме замечаний запиши в спеку (раздел в конце +
   поле frontmatter `review:`).
3. **Красный verify = не оставлять полуфабрикат:** либо доведи до зелёного, либо откати ветку
   (`git switch main` + удали `feature/<slug>`), пометь идею в `FEATURE_IDEAS.md` проблемной и не пиши в каталог.

## 4. Коммит на ветке (без пуша)
- Закоммить на `feature/<slug>`:
  ```bash
  git add -A && git commit -m "feat(<slug>): <title из спеки>"
  ```
  В конце сообщения коммита добавь строку-трейлер `Co-Authored-By:`, требуемую окружением.
- **НЕ пушить и НЕ открывать PR без явной просьбы.** (Пуш в `main` триггерит автодеплой на :8800 — фичу
  туда только через merge человеком.)

## 5. Обновить контекст (бэклог + каталог)
- В спеке выставь `status: done`, заполни `verify:` (pass/fail), `review:` (ok / кратко), `branch: feature/<slug>`.
- Помень идею в `FEATURE_IDEAS.md`: соответствующую `- [ ] <slug>: …` → `- [x] <slug> (feature/<slug>)`
  (или перенеси в секцию «Сгенерировано»).
- Пересобери каталог: `python3 .claude/skills/feature-build/catalog.py` (обновит корневой `FEATURES.md`).

## 6. Отчитаться
Кратко: что реализовано по слоям, результат verify + code-review, имя ветки, переиспользованные скиллы,
и что осталось (push/PR/merge — за пользователем). В автономном режиме — следуй СТОП-условиям `.claude/AUTODEV.md`.
